# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PHC MSDS Compliance Tracker for Al Shifa Laboratory — compliance tracking plus an
AI drafting assistant for the Punjab Healthcare Commission's Minimum Service Delivery
Standards (MSDS, Clinical/Pathology Laboratories): 118 indicators, 37 standards, 10
domains. Two sections:

- **Section A — Compliance Tracker**: indicator registry, daily due-list for recurring
  evidence, compliance scoring, single-button print pack for PHC visits.
- **Section B — AI Drafting Assistant**: drafts SOPs/policies (one-time indicators) and
  reusable templates (recurring documentary indicators), grounded in each indicator's
  compliance requirements. Every draft requires human approval before it counts as filed
  evidence — never auto-published.

**Current state: pre-code scaffold.** `backend/` and `frontend/` contain only placeholder
directories (`.gitkeep`) and READMEs describing intended structure — no Django project,
no Vite project, no dependencies installed yet, no tests, no CI beyond a placeholder. There
are no build/lint/test commands to run until Stage 0 scaffolds the real projects (see
`backend/README.md` and `frontend/README.md` for the exact commands to use when doing so:
`django-admin startproject`/`startapp`, `npm create vite@latest . -- --template react-ts`
+ Tailwind — let the frameworks generate `manage.py`/`settings.py`/migrations/
`vite.config.ts`/`tsconfig.json` rather than hand-writing them).

## Stack

Django + DRF (backend) · React + Vite + TypeScript + Tailwind (frontend) · PostgreSQL ·

## Build process — read `BUILD_PROMPT.md` in full before writing any code

`BUILD_PROMPT.md` (v2) is the current master build document — hand it whole to a
coding agent. It **supersedes** the older "stop after every stage for human
confirmation" flow described in `AGENTS.md` (see
`docs/decisions/0002-frequency-resolution-and-quality-gates.md`): the agent now
verifies each stage against an explicit, automated **Quality Gate** (exact record
counts, split checks, fixture tests — spelled out per stage in `BUILD_PROMPT.md`)
and proceeds to the next stage on its own once every check in that gate passes, in
one run: Stage 0 → Stage 1 → Stage 2 → Section B.

**Decision points: park, don't stop.** Per
`docs/decisions/0003-park-dont-stop.md`, hitting a genuine gap (something
`AI_DEV_PACK.md`/`docs/decisions/` doesn't answer) no longer halts the whole build.
Instead: implement the smallest safe stub for that one piece, mark it in code
(`# PARKED: see docs/status/PARKED_DECISIONS.md #<n>`), log it in
`docs/status/PARKED_DECISIONS.md` (what was hit, the stub, what needs deciding),
mark the affected Quality Gate check "Deferred (parked #n)" — not Pass/Fail — and
keep building everything that doesn't depend on it. Resolve everything in that file
in one pass after the run rather than one at a time.

**Two rules that are never quality-gated and never park-able** (a passing gate or
a parked item never overrides these — if either would be violated, the
implementation is wrong; fix it, don't loosen the rule):

1. **No silent invention of a rule already decided.** Every business rule was
   deliberately decided — see `docs/decisions/` (append new `000N-*.md` files per
   batch, never edit existing ones) and `AI_DEV_PACK.md`. Parking is only for
   genuinely *undecided* specifics, not a way to defer something already answered.
   Examples that must never be invented: due dates, grace periods, scoring
   thresholds, retention windows, valid category/frequency values, print pack
   contents, or a `structured_form` indicator's exact field set if it isn't
   obvious from `compliance_requirements`.
2. **No automatic publishing in Section B.** A generated document or template is
   a `Draft` with `status=draft` until a human explicitly approves it. Nothing
   generated by AI becomes filed evidence, gets written to `is_current=true`, or
   appears in a print pack without that approval step — not even for testing
   convenience (write a separate seed/fixture script instead). This is a
   permanent runtime behavior, not a build-time checkpoint to relax once tests
   are green.

**Data integrity.** `docs/data/indicators_master.json` (118 records) is the canonical,
locked indicator registry. Do not hand-edit it or regenerate it from the source MSDS
manual — that extraction/classification work is already done and reviewed. If the loader
needs to transform it, do so in code, leaving the source file untouched. (Note: an
untracked duplicate `indicators_master.json` currently also sits at the repo root —
treat `docs/data/indicators_master.json` as the one true source.)

**Definition of done, per stage.** Each stage's Quality Gate in `BUILD_PROMPT.md` is
the definition of done — don't mark a stage complete until every check passes (or is
explicitly deferred/parked). Spot-check against the source data; don't just confirm
the code runs. Current progress is tracked in `docs/status/DEVELOPMENT_STATUS.md`
(update it as stages complete) — check `docs/status/PARKED_DECISIONS.md` after any
build session for open items.

Stage order:
1. **Stage 0** — Indicator Registry + Lab Profile, read-only (current stage)
2. **Stage 1** — Recurring entry + daily due-list + compliance scoring
3. **Stage 2** — Print/export engine
4. **Section B** — AI drafting assistant (parallel track, starts once Stage 1 is stable)

## Architecture

### Data model (from `AI_DEV_PACK.md` §5, `BUILD_PROMPT.md`)

```
Domain            id, code (e.g. "ROM"), name
Standard          id, domain_id, standard_no, code (e.g. "ROM-1"), title
Indicator         id, standard_id, text, weightage (100|80), allows_partial (bool),
                  category (physical|one_time|recurring),
                  frequency (nullable; daily|weekly|monthly|quarterly|biannual|annual|as_needed),
                  evidence_format (photo|document|structured_form),
                  compliance_requirements (text), survey_process (text) — reference only,
                  retention_months (nullable, default from category)

EvidenceRecord    id, indicator_id, period_label (nullable for as_needed),
                  submitted_at, submitted_by,
                  status (fully_met|partially_met|not_met),
                  payload (file ref and/or structured field values),
                  is_current (bool — true for the one live record on physical/one-time indicators)

ComplianceSnapshot (computed, not stored)
  per indicator: current status + evidence age
  overall: earned weightage / possible weightage across all 118

Draft (Section B)  id, indicator_id, kind (document|template), content, generated_at,
                  status (draft|approved|rejected), reviewed_by, reviewed_at, version_no

LabProfile         lab_name, address, phc_registration_no, supervising_pathologist
```

Exact splits the Stage 0 Quality Gate checks against (see `BUILD_PROMPT.md` for full
gate list) — treat these as ground truth when something looks off:
- 118 indicators total, IDs `{1..118}`. Domains: AAC 9, BSBS 18, COP 6, FMS 11, HRM 16,
  MER 13, PRE 7, QA 16, ROM 13, RRS 9. 37 distinct Standards.
- Weightage: 97 @ 100, 21 @ 80 (`allows_partial=true` count == 21).
- Category: physical 29, one_time 32, recurring 57.
- `evidence_format`: photo 69, document 44, structured_form 5.
- Recurring frequency distribution (57 total): annual 18, monthly 18, quarterly 8,
  as_needed 7, daily 4, weekly 1, biannual 1 (per
  `docs/decisions/0002-frequency-resolution-and-quality-gates.md` — the 42
  `periodic_unspecified` indicators were each assigned a frequency by manual judgment
  since the PHC manual itself doesn't mandate a cadence for them; flag any that don't
  match how the lab actually runs).

Key mechanics:
- Physical and one-time indicators keep exactly **one** `is_current=true` EvidenceRecord,
  replaced on re-upload. Recurring indicators accumulate one EvidenceRecord per
  `period_label` (daily → `YYYY-MM-DD`, weekly → `YYYY-Www`, monthly → `YYYY-MM`,
  quarterly → `YYYY-Qn`, biannual → `YYYY-H1`/`YYYY-H2`, annual → `YYYY`), pruned past
  the retention window (default 12 months). `as_needed` indicators are event-triggered,
  not period-keyed — logged per occurrence with a timestamp, never on the due-list.
- Compliance scoring is 3-tier, not binary: `fully_met` = full weightage (100 or 80 per
  indicator), `partially_met` = 80% weightage (only for the 21 `allows_partial`
  indicators), `not_met`/no record = 0. Uses each indicator's **most recent** record, not
  specifically the current period's. "100% compliance" = earned weightage ÷ possible
  weightage across all 118, computed live — not a simple "evidence exists" count.
- Due-list is presence-only: "has this period's evidence been entered yet, yes/no." No
  deadline/lateness state — an entry made late counts the same as one made on time.
  Physical/one-time/`as_needed` indicators never appear on it.
- Section B produces two distinct draft objects: **document** drafts (one-time indicators
  — the AI drafts the actual SOP/policy; on approval it *becomes* that indicator's current
  evidence, superseding not deleting the previous record) vs. **template** drafts
  (recurring documentary indicators — the AI drafts a reusable format staff fill in each
  period; the filled instance, not the template, is the EvidenceRecord — approving a
  template never creates/modifies an EvidenceRecord). The single most load-bearing test
  in the whole build: no `Draft` with `status=draft` or `status=rejected` is ever
  readable from any evidence/print-pack query path.

### Intended app/page boundaries

Backend (`backend/apps/`):
- `registry/` — Stage 0. Domain, Standard, Indicator, LabProfile models; read-only
  filterable view.
- `evidence/` — Stage 1. EvidenceRecord model, daily due-list logic.
- `compliance/` — Stage 1/2. Compliance % computation.
- `exports/` — Stage 2. Print/export engine, ordered to mirror PHC's own domain →
  standard → indicator numbering (mirrors the assessor's own checklist).
- `drafting/` — Section B. Draft model, generation via the Anthropic API, human
  review/approval workflow.

Frontend (`frontend/src/`):
- `pages/registry/` — Stage 0 registry UI.
- `pages/daily/` — Stage 1 due-list + evidence entry form.
- `pages/print/` — Stage 2 print pack trigger + preview.
- `pages/drafting/` — Section B generation UI + review/approve screen.
- `lib/api.ts` — single place for API base URL + fetch wrappers.
